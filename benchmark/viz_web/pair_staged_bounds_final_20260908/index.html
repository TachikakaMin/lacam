Pair 不再先算完所有候选，40×40 从 6/9 提到 8/9

之前虽然已经复用了增量 Hungarian，但每次货架状态变化后，很多候选边会先 重跑一遍 8 步 prefix 模拟。最贵的工作发生在 Hungarian 之前，所以匹配器 本身变成 incremental 以后，总时间仍然没有明显下降。

正式协议：full 518，14 workers，每例 10 秒，seed 0，unit weights。 对比基线二进制 02a53b… 与当前二进制 855f1f…。

结果：full 从 485/518 提到 487/518，没有丢解。 40×40 dense-channel 从 6/9 提到 8/9。共同成功的 485 例中， 1 例更好、484 例相同、0 例变差。唯一仍未在 10 秒内完成的是 b9 / 32 robots / 48 targets。

这次改了什么

新代码给每条 target-goal 边分三档。第一档只算考虑墙体的最短距离，再加 必需的 Lift/Drop，成本很低；只有当前匹配选中的边，或仍可能达到或优于当前 最优代价的边，才继续做 prefix 模拟和完整 PairCost。

旧路径 状态变化 → 所有失效候选先做 8 步 prefix → 增量 Hungarian → exact certificate 当前路径 状态变化 → 失效候选退回 CHEAP_BOUND → 选中或仍有竞争力：PREFIX_BOUND → 还需证明：EXACT → 同一份增量 Hungarian 只 repair 变化的行

Hungarian 没有换算法。Pair 继续使用 LaCAM-TAPF 现有的增量 primal/dual 核心；forced-edge 检查复制当前状态，只限制一行后调用同一个 repair_rows()。最终被选中的边全部精算到 EXACT，没有精算的边则由 forced lower bound 证明不可能进入 最优匹配，因此 tau_guide 的结果仍与完整 PairCost 矩阵一致。

为什么 b9/r32 还需要 24 秒

这例有 48 个 target，每个 target 有 32 个同 block 边缘 goal，一轮就是 1536 条候选边。b9 的边缘格很多，单靠 wall distance 得到的 cheap bound 彼此很接近，无法像 b3、b4 那样快速排除大部分候选。

30 秒诊断在 24.146 秒取得首解，26.979 秒结束，最终为 (134, 3441)。 期间只做了 2 次 full Hungarian，却做了 399,728 次 forced row repair； 246 个 upper epoch 平均约 1625 次，和每轮 1536 条候选边处在同一数量级。 这说明 incremental Hungarian 已经生效，剩下的问题是每轮仍要证明太多边 “不会赢”。

这次运行的 guidance 为 26.394 秒，占总时间 97.8%。其中 vacancy potential 2.957 秒、timed transport 0.219 秒，ρ 的几个计时项合计约 1.023 秒。 其余 guidance 目前没有细分到 Pair certificate 和 task compiler 的独立毫秒数， 所以不能只凭调用次数断言它们各占多少。下一步应先补这两个计时，再考虑复用 跨 epoch 的 forced certificate，或给 b9 这类大 goal set 增加更强但仍可采纳的 中间下界；继续改 Hungarian full solve 不会解决主要问题。
