Pair 增量 Hungarian：实现正确，整体没有加速

这次改动把 Pair lazy certificate 接到了 LaCAM-TAPF 已有的增量 Hungarian 核心上。代码复用、正确性和兼容性都通过了，但正式 518 例结果没有显示整体性能收益。

正式协议：14 workers，每例 10 秒，seed 0，unit weights； full = quick 77 + factorial 432 + 40×40 dense-channel 9。

结论： 这是一个正确的共享核心重构和增量实现，但还不是有效的整体性能优化。 full 的 solved set 完全不变，累计 solver time 增加 5.8 秒； 40×40 仍为 6/9。后续若继续优化，应先补 Pair 阶段的独立耗时统计， 再判断开销来自 row repair、forced certificate，还是其他 guidance 工作。

代码到底复用了什么

tapf_assignment.hpp
  IncrementalHungarianState<Scalar>
  ├── solve_full()
  ├── repair_rows()
  └── 唯一的 augment / dual update

TAPFAssignmentState
  └── 整数 cost 与 stable tie 适配

Pair lazy certificate
  └── long double、INF、deadline 适配
      ├── 跨 upper epoch 恢复 primal/dual state
      ├── 只 repair 发生变化的 target rows
      └── forced edge 在状态副本上单行 repair

仓库里只剩一份增广路径和 dual 更新循环。Pair 层不再维护第二套 Hungarian。若浮点 dual invariant 已损坏，代码会显式报错，不会偷偷 退回一次 full solve。

验证与未解决问题

  • C++：423 / 423 通过，包括原 TAPF compatibility。
  • benchmark gate：11 / 11 通过；独立 GPT-5.6 Sol/high 审查 APPROVE。
  • quick 77：逐例零语义差异。
  • full 518：4 个成功计划 SHA 变化，其中 3 个 cost 相同、1 个 cost 回退。
  • 当前 CSV 没有 Pair Hungarian 的独立毫秒统计，因此只能确定“整体未加速”， 还不能精确拆出 row repair 与 forced certificate 各占多少时间。
