先看结论

  • 正确性与覆盖：正式 full 为 479/509； 新增 factorial 为 432/432，30 个失败全部是原 quick 中的大图 timeout：g20x20 timeout×6；g40x40 timeout×8；g80x80 timeout×16。
  • 主要收益：相对隔离保存的 pre-v5 历史 full， 共同成功例的 makespan 几何比为 0.801 （小于 1 更好），B/E/W=348/85/46。
  • 明确代价：次级 work 几何比为 1.028，B/E/W=136/88/255；wall time 从 49.2s 增至 295.6s，约 6.0 倍。
  • 不能夸大：E1/E2 在 quick corpus 上没有证明聚合 质量收益；E4 确实改善若干方案，但消耗更多运行时间。

问题到底是什么？

两个目标，先后有别

T（makespan）是最后一个任务完成的拍数，先最小化它； W（work）是搬货、空驶、Lift/Drop 等动作的加权总量，只在 T 相同的时候比较。实现使用 10-6 定点整数，避免浮点误判。

最难的是“搬到一半”

货架进入通道后，当前局部任务可能因重新编图而消失，但物理上的 货架仍在机器人手里。v5 用稳定的 TransferId 和 custody 记住“谁在搬 哪个货架、最终放到哪里”，路线暂时不可用也不会把任务当作不存在。

仍是单一路径，只增加必要机制

1 · PlanCost(T,W)首次完成前缀与严格词典序
2 · TransferId跨 epoch 保留货架与搬运身份
3 · 因果准备前驱正在清障时，下游可先靠近
4 · 时序协调同一通道可错时复用，不做永久封路
5 · 有界改进同一控制器内尝试更小的 (T,W)

这些机制都接在原来的节点扩展、constraint tree、 funcPIBT()、apply_ops()、两遍候选、repair 和 final replay 上；没有平行 planner、实例特判或 legacy fallback。

一个具体例子：Testcase C

6 台机器人要搬 6 个目标货架。旧的局部策略容易把通道里的货架视为 “任务已经变了”，后续机器人也不知道能否提前准备。当前 production 得到 T=31, W=93，共 49 次 loaded move、 32 次 free move、12 次 Lift/Drop， 0 anonymous move、0 reversal。W 不宣称最优。

为什么相信这些数字？

  • 285 项 C++ 与 155 项 Python 测试全绿；每个成功 plan 都由权威 Python validator 再重放，并精确核对定点 W。
  • full 先由独立 GPT-5.6 Sol/xhigh 审查，approval 同时绑定 binary、 suite definition 和 semantic corpus。
  • worker 只读取 Linux sealed memfd 中的二进制和 509 份 YAML； 本轮 provenance 为 sealed_linux_memfd。
  • 第一次 full 虽完成 solver task，却在发布前 memfd 重哈希路径处 fail-closed，没有 rows/timing。该缺陷先新增 RED regression，再修复、 跑完整 Python 测试并由另一位独立 xhigh reviewer 重新批准后重跑。

仍然存在的限制

  • 30 个原 BRaP 大图在 10 秒内仍 timeout；v5 没有提高成功率。
  • W 经常比历史实现更大，Testcase C 也只证明 T 达下界，不证明 W 最优。
  • 首解后的有界改进让正式 full wall time 约为历史运行的 6.0 倍；这是清楚可见的质量—时间交换。
  • 432 个 factorial case 是构造可解、受保护的随机配对集合；它扩大 覆盖面，但不能替代真实仓库流量分布。
