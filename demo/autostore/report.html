顶部吊运机器人搭积木：从仓库算法到 3D 建造

基于 Carrier-LaCAM（dd-lacam-next）的增量扩展 · v2 · 2026-09-20

1. 问题是什么

一块格子地面上方架着轨道平面，几台机器人在轨道上跑，每台带一根竖直吊绳，一次吊一块单位立方体的彩色积木。积木随机堆放在地面格子上（每格是一根可叠高的"列"），要把它们重排成指定形状和颜色的目标结构。硬约束：

① 只能吊每列最顶上的砖（被压住的要先"挖"出来）；② 砖数与目标结构精确相等，没有足迹外的缓冲区——挪开的砖只能放在足迹内的空格或别的砖顶上；③ 目标结构可以有悬空部分（桌面板下方全空，靠侧面连接传力到腿）。这里假设相邻体素接触面是刚性连接（类似乐高卡扣，可传拉力剪力），只验证连通性、不算力矩强度；④ 吊运耗时按行程计：绳子下放到深度 d 再收回要 2d 拍，吊放期间机器人不可打断。

三个测试场景（页面导航可切换动画）：整板搭桌子（5×5 板=桌子足迹，悬空桌面）、木马（3×7 板，高 7 层，悬空马身+悬挑头尾）、高密度重排（近满载砖库原地重排成分层配色，含 3 个"透明暂存格"——不属于目标结构、专用于腾挪的空列）。

                          z=1   █                  █   ← 腿

2. 总体架构：三个时间尺度

层做什么节拍
任务编译层（Python）第三维物理：支撑/封存/挖掘/暂存，递归编译出"搬哪块、去哪、先做谁"每个事件重跑一次
路径求解层（C++，Carrier-LaCAM）二维轨道平面：任务分派给谁、怎么走、怎么避让每段一次求解
服务时钟（Python 执行器）吊放的多拍服务：占用格子、倒计时、完成落账逐拍

能这样切的前提是吊运模型规定：载荷先收绳到高于最大堆高的运输高度再水平移动，落地砖不挡机器人，"走路"退化成纯二维问题。而"何时能拿/能放"全是第三维的事，由编译层显式规则把关。

术语：Carrier-LaCAM本项目扩展的多机器人搬运求解器（LaCAM 搜索 + 货架搬运层）；体素三维网格中的一个单位小方块；gantry顶部轨道吊运模式；makespan/T模拟总拍数；Task-BR递归任务编译——做 A 先递归安排 A 的前置任务，走不通就回退换方案；serving吊放服务窗口，期间机器人被占用；rhoC++ 内把就绪任务匹配给机器人的分派器；BFS广度优先搜索，本文用来检查每块砖是否仍能连到地面；snapshot/rollback先保存模拟状态、分支失败后恢复；anytime先给一个可行解、剩余时间持续改进的求解方式；JSONL每行一条 JSON 记录的日志格式；TDD先写会失败的测试再实现到通过；guidance求解器内部的任务编译与代价估计层；lifelong任务持续到来、边执行边规划的运行模式。

3. 底层：C++ 求解器的 gantry 扩展

原求解器是密集仓库语义：载货机器人不能穿过落地货架，货架逐格倒手。吊运不同，故做了一组由 flags: {gantry: true} 开关的增量修改（关掉时 77 个仓库基准逐行零差异）：

模块仓库语义gantry 语义
碰撞校验 apply_ops()所有货架同格互斥只有落地砖互斥；空中载荷不与落地砖冲突
搬运路线相邻存储格逐跳，BFS 遇存储格即停吊起直达终点；只有落点被占才需清障
任务就绪看路线第一步看落点
状态投影货架只有位置位置 + 已安装/被吊着模式位
初始状态全空载开局carrying 字段：机器人可吊着砖冷启动
返回时机anytime 烧满时限做改进DD_FIRST_SOLUTION_ONLY=1：拿到首个可行解立即返回，跳过 anytime 改进阶段（事件驱动的段马上会被截断，改进的尾巴不会被执行；默认关闭）

兼容性说明：无搬运目标的普通 TAPF 实例没有货架层，所有 carrier/gantry 分支因数据缺失（kappa 为空）自然短路，代码走原始路径——这是结构性退化，不依赖开关；gantry 开关只区分"仓库搬运"与"吊运搬运"两种有货架层的语义。

量化对照（金字塔实验）：改造前，因为吊/放只计一拍且载货被落地砖挡路，求解器把"每走一格就放下再吊起"当最优策略——35 块砖搬了 399 次；gantry 语义修完后恰好 35 次吊起 + 35 次放下，全部直线送达。

4. 吊运计费与"不可打断的服务"

这是 v2 的核心新增。取放砖的服务时长按吊绳行程计：

服务时长 = 2 × (轨道高度 − 1 − 目标高度z)
  例（桌子，轨道在第 5 层）：从地面 z=0 取砖 = 8 拍往返；
                              往塔顶 z=3 放砖 = 2 拍。

处理方式借鉴了 agent_fable 分支的 service 机制：机器人一旦开始吊放就进入服务状态——从规划实例中移除、它所在的格子在地图上变成临时墙（物理上它悬停在那里占着轨道）、倒计时归零才落账（砖真正离开堆顶/落进目标位）。服务的开始和完成都是触发全局重规划的事件。两个由此产生的并发问题及解法：

其一，服务墙可能把地图切成几块，某些任务的起点/终点被隔断——重规划前做连通性过滤，被隔断的任务本段不派发（墙消失后自然恢复）；吊着砖被封在死角的机器人转入冻结（1 拍伪服务），等墙倒。过滤要迭代到不动点，因为冻结本身会加新墙。其二，极端情况下服务墙围出的死角让整段实例无解（两台机器人挤在 2 格死角无法换位）——逐级降级：先只保留吊着砖的任务重试，再不行就全体冻结 1 拍等墙倒。

5. 中层：事件驱动的重规划循环

循环直到 世界 == 模板：
  1. 读体素世界，编译一批任务（§6）
  2. 写成 gantry 实例：机器人、任务起终点、storage_map、
     carrying（谁吊着砖）、服务墙（@ 格）
  3. C++ 求解器给首解
  4. 逐拍重放，遇事件截断：吊放服务开始 / 服务完成 /
     异地停放（原地放回不截断）；服务中的机器人时钟并行推进
  5. 事件如实落账（堆高、颜色、位置），回到 1

吊着砖的机器人经 carrying 冷启动进入下一段：保留"这块砖归我"的绑定，路线全部重排；目标被占则重选同色目标。

6. 上层：mini Task-BR 递归任务编译器

6.1 物理判据

可放置 placeable(cell, z)：
  ① 通道畅通：该列 z 以上没有砖（吊绳要下得去）
  ② 模板下层已装；③ 反封存：z 以下非模板槽位必须为空
     （否则杂砖被封死在结构底下，而砖数精确守恒）
  ④ 有支撑：落地 / 正下方已装 / 四邻同高有已装的砖

可拿取 removable(cell)：
  ① 只能拿列顶，且顶砖不是已安装结构（结构不是库存）
  ② 拿走后做接地连通性 BFS：剩余砖必须全部经共面相邻连到地面

6.2 递归编译（举例）

要装桌面板 g=(2,3)、z=2，编译器在模拟世界副本（共享事务）上展开：

try_build( (2,3), z=2 )
├─ 清列：(2,3) 列上压着一块杂砖
│    └─ 生成停放任务 → park_spot 选暂存位            [任务①]
├─ 支撑：正下方是空的，查四邻同高
│    ├─ 邻居 (2,2) 的 z=2 已装 ✔（OR 分支命中）
│    │   （都没装则递归 try_build 邻居，失败 snapshot 回滚换边）
├─ 找料：找一块顶上可拿的 top 色砖
│    └─ 都被压住？递归挖掘：把盖着的砖停走            [任务②…]
└─ 生成建造任务：源格 → (2,3) z=2                     [任务③]

三条关键性质：联合性（后编译的目标看得见先编译者占了哪些格拿了哪些砖）、可回退（支撑 OR 分支带 snapshot/rollback）、只下发当下可执行的（依赖链的其余部分下一段按新世界重编译）。

6.3 暂存位选择（确定化）

选位只依赖世界状态、不依赖机器人位置，重复编译收敛到同一决定：优先已完工结构顶（随时可拿走）、其次矮列（把停放分散开——若都挤到少数几根列，两根堆满的列会互相成为对方唯一的腾挪去处，砖被永远倒来倒去）、蛇形序为末键。透明暂存格因"模板为空=永远完工"自动成为高密度场景的首选。

6.4 跨段承诺粘性（v2 新增，按场景开关）

每个事件都全量重编译会让机器人"走到一半被改派"。三项粘性：上一段未启动且仍有效的地面任务原样续签进新事务；吊着砖的机器人优先沿用原目标；目标只是暂时不可放（支撑在途）时冻结等待几拍而不是把砖放下再吊起（等待有上限计数，防互等死锁；计数器要穿透冻结生命周期——这是一个真实修过的 bug）。实测桌子场景 T 降 15%（499→427）、吊起次数 100→84；但木马/高密度场景粘性会制造自己的循环，数据中性偏负，因此做成按场景开关。另一个被小实验否决的尝试：把下发量收缩到空闲机器人数——配额太紧会饿死关键清障任务（T 反升 34%），已回滚。

7. 任务出身埋点：往复的真正来源

为诊断解质量，每个任务记录完整出身链（如 clear(2,3)<-support((2,4),2)<-root(2,3)z2），连同是否下发、是否被机器人实际启动，逐段写入 JSONL。桌子 seed=7（244 段）的统计：

出身类别生成下发实际启动
清列停放55526324（9%）
承诺续签29126536（14%）
root 建造179356
held 目标保持1421402（对吊着砖"启动"无意义，应看完成率）
其余类别（支撑链/前缀建造、held 重定/停放、挖料等）52836116
合计1695106484

两个口径：下发的任务中 92.1%（1−84/1064）未被任何机器人启动；按生成量算则是 95.0%。结论：往复的主要嫌疑不在任务生成，而在"下发→执行"这一跳——831 个任务签名在相邻段重复生成（说明编译本身稳定），但每段任务数（4–5）多于空闲机器人数（1–3），C++ 的 rho 分派器每段在过剩任务里自由改选，最极端的一条停放任务被连续下发 75 段无人执行。粘性护住了任务集，护不住"谁执行"。需要说明：这是埋点数据给出的强指向，尚未做"跨段保留 rho 记忆"的对照实验来确证因果；rho 的段间连续性机制 C++ 里已存在，只是每段冷启动进程把它的记忆清零。

8. 实验结果（每段限时 0.25s，失败按 1s/10s+换种子重试；并行跑，工作目录按种子隔离）

场景板面砖数种子通过T 范围展示轨迹（seed=7）
整板搭桌子5×5（=足迹）336/6332–650T=427，84 次吊起（每砖 2.55 次）
木马3×7（=包围盒）474/4737–1180T=737，99 次吊起（每砖 2.11 次）
高密度重排5×5664/4517–673T=517，102 次吊起（每砖 1.55 次）

每砖至少要吊起 1 次，加上初始堆中被压住砖块的必要挖掘，经验下界约 1.0–1.3（按各场景初始被压砖比例粗估）；当前 1.55–2.55 与之的差距，§7 的埋点数据指向 rho 段间漂移是主要候选解释（未做消融确证）。可视化采用单物体渲染：每块砖一个持久网格，位置由导出的逐砖时间线（静止段/吊运段/随车段）每帧计算，位置连续性由数据结构保证——这替代了曾多次出 bug 的"静态砖↔手上载荷↔动画"三方交接方案，网格数还更少。

9. 正确性怎么保证

三道闸门。C++ 侧：apply_ops() 裁决二维任务语义（机器人相撞、落地砖同格、非法吊放；三维支撑/颜色/封存归 Python），gantry 与 carrying 扩展共 9 个 TDD 单元测试。Python 侧：每次放砖跑接地连通性 BFS、停放限高断言、每个事件核对执行机器人当拍坐标（防"传送"）、逐砖时间线的段间连续性校验。终态：逐体素与模板比对 + 总砖数守恒 + 全局连通性。在冻结的 77 个仓库基准上，C++ 改动前后 solved/makespan/加权代价逐行相同。

10. 已知短板与下一步

① 最可疑的结构性根因：每个事件重启求解器。它同时关联三件事——rho 分派记忆清零（§7 中 92% 的下发未被执行）、guidance 每段重建（每段 30–100ms 固定开销 × 数百段）、以及服务墙死角这类只在"分段快照"视角下才存在的伪死锁。候选方案是把事件循环搬进 C++：serving 作为带剩余时长的机器人状态进搜索内核、lifelong 化多任务波次、rho 连续性跨段存活。在已尝试的范围内，编排层修补收益递减（v2 粘性实验：一个场景 -15%，另两个中性偏负）。

② 多机吊砖冷启动的解质量。多台机器人都吊着砖开局时偶发超时或极差首解（一次观测到 makespan 23795），现靠时限梯度+换求解器种子兜底；预期会随①缓解，但未验证。

③ 编译器还在 Python。它是 C++ 仓库版递归编译器（resolve_shelf_task_br_pibt）的三维镜像（共享事务↔transaction、OR 回退↔candidate rollback、暂存选位↔vacancy 选择），下沉到 C++ 后与搜索在同一状态空间联动；"整板+悬空+贪心失败"的历史用例是现成验收测试。

11. 一句话总结

把 3D 建造拆成"体素世界的递归任务编译（支撑/封存/暂存/依赖）+ 二维轨道的多机器人搬运（分派/路径/避撞）+ 逐拍的吊运服务时钟"，用事件驱动重规划和吊砖冷启动缝合。仓库算法的 LaCAM 搜索循环与 PIBT 生成器未改动，碰撞语义、搬运路线编译、任务就绪判定与状态投影按吊运物理扩展后，密集腾挪从二维路径层消失、转移到第三维的建造次序与暂存决策；埋点研究进一步显示，下发任务的 92% 未被执行、任务集在段间高度重复——最强的候选解释是跨段分派记忆的缺失，这为下一步"事件循环进 C++"给出了量化的（但尚待消融确证的）依据。
