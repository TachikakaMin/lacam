5. replan stability / goal commitment；
6. service duration interaction；
7. congestion / region capacity handling；
8. runtime engineering / cache / data structure；
9. env state-machine invariant or accounting issue；
10. one deliberately different algorithmic direction。

每条 hypothesis 必须包含：

- hypothesis_id；
- observed_pattern；
- suspected_code_path；
- causal_chain；
- proposed_change；
- expected_metric_signal；
- possible_regression；
- minimum_experiment；
- why_this_is_not_seed_hardcoding；
- estimated_implementation_cost。

不允许在没有 hypothesis_id 的情况下实现代码改动。

如果某个改动只是 heuristic 常数调整，它必须明确说明：

- 该常数对应哪个实测瓶颈；
- 为什么现有值造成该瓶颈；
- 预期哪个 diagnostic signal 会改变；
- 为什么这不是围绕 quick seeds 的盲目拟合。


====================
探索原则
====================

不要把优化过程理解为某个预设方向的参数搜索。除了硬约束和固定评测场景外，不要预设 assignment、planner、service-goal、cache、runner 或 env 哪一层一定是正确切入点。

每一轮都先从当前证据出发建立根因假设。可以使用：

- trajectory；
- trace；
- schedule；
- stdout / stderr；
- runtime profile；
- 代码路径；
- 状态转移不变量；
- 任务生成分布；
- planner search statistics；
- assignment 输入输出；
- service duration 语义；
- cache 命中行为；
- goal churn；
- local congestion；
- failure / timeout / empty solution 计数。

优先寻找“为什么 throughput 被浪费”的本质原因，而不是只调已有启发式常数。

可以修改：

- 数据结构；
- 状态表示；
- 目标构造；
- replan / commit 策略；
- search / assignment 交互；
- cache 边界；
- benchmark harness 的内部工程实现；
- 可复用 instrumentation；
- 可复用测试或工具。

但任务 / agent 状态机、env accounting、validity checking、throughput / completed_tasks 计算只能做 instrumentation、refactor 或有测试支持的 bug fix，不能改变固定场景语义。

对任何候选改动，必须说明它作用在哪个因果链条上：

- 观察到的低效行为是什么；
- 该行为由哪段代码、状态表示或算法假设导致；
- 改动如何改变这个因果链条；
- 预期会改善哪个可观测指标；
- 可能牺牲什么；
- 如何用 quick / final 结果验证。

允许做更本质的重构或算法替换，而不是被限制在轻量 heuristic tuning。

不要因为某个方向之前有效或无效就机械重复。只有当新的 trajectory evidence 给出不同根因解释时，才沿相似方向继续；否则换层次、换假设、换观测方法。

如果当前 trace 指标不足以解释根因，可以先补充通用 instrumentation 或分析脚本。

这些工具必须：

- 写入 RUN_DIR；或
- 作为可复用工具 / 测试进入源码目录。

禁止通过修改结果文件来制造结论。


====================
Diversity requirement
====================

进入 final eval 前，除非 budget 异常耗尽，search trials 必须至少包含一次来自以下类别的代码尝试或明确 falsification：

1. assignment / cost / task choice；
2. loaded batching vs delivery policy；
3. service goal selection or goal set construction；
4. planner search behavior / focal ordering / conflict handling；
5. replan stability / goal churn reduction；
6. congestion or service-region blocking；
7. runtime / cache / engineering optimization。

某个类别可以被标记为 "falsified without code change"，但必须在：

  RUN_DIR/falsified_directions.md

中写出具体理由，包括：

- baseline diagnostics；
- code inspection evidence；
- 为什么该方向当前不值得消耗 benchmark budget。

不要把超过 50% 的 pre-final benchmark runs 花在同一种 causal mechanism 的变体上。

尤其不要反复微调：

  loaded_distance_since_last_delivery

或类似 loaded pickup distance scalar，除非 diagnostics 显示了一个新的、具体的 loaded-agent failure mode，且上一轮 0.75x 改动没有覆盖这个 failure mode。

diagnostic_summary 至少包含：

====================
Best quick simplification rule
====================

每次发现新的 best quick score 时，不要立刻扩大改动。

先进入一次代码简化阶段：

1. 保存当前完整 diff 到：

   trial_dir/raw_candidate.diff

2. 删除没有贡献的参数、分支、实验性 dead code、临时调试输出和偶然改动。

3. 保留能解释 throughput 提升的最小实现。

4. 该最小实现必须对应当前 hypothesis_id 和 causal_chain_claim。

5. 如果 budget 允许，重新跑 QUICK_EVAL_SEEDS，确认 quick score 没有实质下降。

6. 如果简化版相对 raw candidate 的 quick throughput_mean 下降超过 0.001，则恢复 raw candidate，除非 diagnostics 显示 raw candidate 是过拟合、invalid 或语义风险更高。

7. raw 和 simplified 的结果都要写入 trials.jsonl。

8. simplification rerun 计入 benchmark budget。

9. 如果 simplification 会导致剩余 budget 不足以完成 FINAL_EVAL_RUNS，则不要启动 simplification，直接记录原因。


====================
优化目标
====================

主指标：

  throughput

按 FINAL_EVAL_SEEDS 的 mean 判断。

必须满足：

  所有计入结果的 row 都有 valid=1。

同分或近似同分时优先选择：

1. 更高的 completed_tasks mean；
2. 更高的 alternating_throughput mean；
3. 更低的 total_planner_runtime；
4. 更低的 total_assignment_runtime；
5. 更少的 planner timeout / failure / empty-solution 计数；
6. 更小、更可解释、更语义安全的 diff。


====================
停止规则
====================

pre_final_runs_used < PRE_FINAL_RUN_MIN 时，不要因为暂时平台期、已经超过 baseline、或短期没有新想法就停止。

必须继续尝试新的通用算法改动、工程优化、diagnostic-guided falsification 或更换切入层。

只有当：

  pre_final_runs_used >= PRE_FINAL_RUN_MIN

且：

  total_runs_used + FINAL_EVAL_RUNS <= TOTAL_BENCHMARK_RUN_BUDGET

时，才允许停止搜索并进入 final eval。

停止前必须对最终候选跑 FINAL_EVAL_SEEDS，并和 baseline FINAL_EVAL_SEEDS 做同 seed 对比。


====================
Final evaluation
====================

在 pre_final_runs_used >= PRE_FINAL_RUN_MIN，并且剩余 budget 足够完成 FINAL_EVAL_RUNS 后，选择 best candidate。

选择规则：

1. highest quick throughput_mean；
2. 如果 within 0.002，则选 completed_tasks_mean 更高者；
3. 如果仍接近，则选 alternating_throughput_mean 更高者；
4. 如果仍接近，则选 total_planner_runtime_mean + total_assignment_runtime_mean 更低者；
5. 如果仍接近，则选 timeout / failure / empty-solution 更少者；
6. 如果仍接近，则选 diff 更简单、causal-chain evidence 更清楚、语义风险更低者。

然后运行 FINAL_EVAL_SEEDS：

- baseline commit `BASELINE_COMMIT`，即运行开始时的 latest-code baseline；
- selected best candidate。

final 决策只基于 paired FINAL_EVAL_SEEDS comparison。

final_eval.csv 必须包含：

- one row per seed for baseline；
- one row per seed for best；
- one paired delta row per seed；
- one mean row；
- one win / loss / tie summary。

所有 final rows 必须 valid=1。

如果任何 best candidate final row 有 valid != 1，则 candidate rejected。如果 budget 允许，评估 next-best valid candidate。如果 budget 不允许，诚实报告失败，不要伪造或补写结果。

quick / final 所有 seed 都必须使用下面的参数形状。不同 seed 只能改变：

- SEED；
- result.csv 输出路径；
- schedule.yaml 输出路径；
- stdout / stderr 保存路径。

    0 \

    1 \
    2 \
    0 \

    5 \

====================
执行循环
====================

按以下顺序执行：

1. Create RUN_ROOT_DIR and RUN_DIR。

2. Record：

   - git rev-parse HEAD；
   - git status --short；
   - cmake build log；
   - ctest log。

3. Verify HEAD is clean latest-code baseline and save `BASELINE_COMMIT=$(git rev-parse HEAD)`。

4. Run baseline quick on seeds 0,1,2 at BASELINE_COMMIT。

5. Inspect actual output schemas：

   - schedule.yaml；
   - result.csv；
   - result.csv.trace.csv；
   - stdout；
   - stderr。

6. Create trajectory analyzer：

   RUN_DIR/tools/analyze_trial.py

7. Analyze baseline quick schedules / traces and write：

   - RUN_DIR/baseline_observations.md；
   - RUN_DIR/hypotheses.jsonl。

8. Iterate until pre_final_runs_used >= PRE_FINAL_RUN_MIN and enough budget remains for final eval：

   a. Select a hypothesis_id not already exhausted。

   b. Implement the minimum code change needed to test it。

   c. Build。

   d. Run quick benchmark seeds 0,1,2, or a justified smaller diagnostic seed set if budget control requires it。

   e. Save stdout / stderr for every seed。

   f. Run trajectory analyzer for every seed。

   g. Append trials.jsonl with causal-chain evidence。

   h. If new best quick, simplify diff and rerun quick if budget allows。

   i. If invalid rows or semantic-risk changes appear, revert or fix before continuing。

   j. Do not spend more than half of pre-final runs on variants of the same mechanism。

9. Select final candidate using quick score, diagnostics, semantic safety and tie-break rules。

10. Run final baseline and final candidate on seeds 0..9。

11. Generate：

   - README.md；
   - trials.jsonl；
   - summary.csv；
   - sample_efficiency.png；
   - best_patch.diff；
   - final_eval.csv；
   - baseline_observations.md；
   - hypotheses.jsonl；
   - falsified_directions.md。

12. Final response should only summarize：

   - RUN_DIR；
   - baseline final mean throughput；
   - best final mean throughput；
   - paired seed deltas；
   - whether all final rows valid=1；
   - total benchmark runs used；
   - code files changed；
   - main trajectory pattern；
   - why the selected change targets that pattern；
   - failed directions；
   - exact reproduction commands。
